## 二、标准操作流程

### 1. 定位加密点（最关键）
- **全局搜索**：在 Sources 面板 `Ctrl+Shift+F` 搜索关键词，如 `sign`、`encrypt`、`token`、`password`、`appKey`、`nonce`、`timestamp`
- **XHR 断点**：Network 面板选中请求 → 右键 → `Break on` → 看调用栈（Call Stack）回溯到加密函数
- **DOM 事件断点**：对提交按钮设置事件断点，顺调用栈找触发链

### 2. 下断点调试
- 在可疑函数行号处点击打断点，刷新触发
- 观察 **Call Stack**（调用栈）、**Scope**（作用域变量）、**Watch**（监视表达式）
- 逐步执行（Step Into / Step Over），记录关键变量值

### 3. 分析加密逻辑
- 常见算法识别：MD5、SHA1、SHA256、AES、DES、RSA、Base64
- 看参数拼接顺序：`sign = md5(timestamp + nonce + params + secret)`
- 注意动态密钥（从某个接口获取）、时间戳校验、参数乱序等防护

### 4. 还原与验证
- **纯算法还原**：找到算法后用 Python/Node.js 重写
- **补环境**：扣取加密 JS 代码，用 Node.js + jsdom / vm2 补浏览器环境（`window`、`document`、`navigator`）
- **浏览器直接调用**：`Runtime.evaluate` 或保存整个加密函数到本地文件
- 验证：用还原出的签名请求一次接口，比对返回结果

## 三、常见防护与对策

## 一、JS 逆向原理

一句话：**从"前端能正常跑起来"这个结果，反推出"参数是怎么算出来的"，然后在外部环境里自己复现一遍。**

一个网页能正常请求数据，必然经历：

```
用户点按钮 → JS 收集参数 → JS 生成签名/加密 → 浏览器发 HTTP 请求 → 服务端校验 → 返回数据
```

服务端要校验的签名（sign、ckey、token），是前端 JS **在浏览器里现算出来**的。JS 逆向就是：

1. **找到**这段计算代码（断点/搜索/调用栈）
2. **读懂**它怎么算的（拼接顺序、盐值、算法）
3. **还原**成你自己的代码（Python/Node），脱离浏览器也能算出同样的签名

本质是**逆向工程**——就像拿到一个黑盒，你不打开它，而是通过输入输出反推内部构造，然后自己做一个能产出相同输出的盒子。

## 二、三者的区别

| 维度 | HTTP 请求 | JS 逆向 | 模拟人工操作（RPA/浏览器自动化） |
|------|-----------|---------|-------------------------------|
| **操作层面** | 直接用协议发请求 | 先逆向出参数算法，再发请求 | 驱动真实浏览器，模拟点击输入 |
| **要不要懂 JS** | 不需要 | 核心就是分析 JS | 不需要，只看界面 |
| **请求参数** | 只发静态参数 | 能自己算出动态签名 | 浏览器自动算好，不用管 |
| **速度** | 最快 | 快（构造请求即可） | 最慢（要渲染页面、等加载） |
| **隐蔽性** | 容易被风控识别（缺签名） | 较高（签名正确，像真请求） | 中等（行为特征可被检测） |
| **难点** | 几乎无 | 还原算法、补环境、抗混淆 | 元素定位、弹窗处理、验证码 |
| **适用场景** | 简单公开接口 | 有签名/加密的接口 | 登录复杂、需要真实浏览器行为 |

## 三、它们的关系（不是互斥，是递进）

```
直接 HTTP 请求 ──(遇到签名/加密)──→ JS 逆向 ──(遇到环境检测/风控)──→ 模拟人工操作
    简单场景                              中间层                              兜底方案
```

- 接口没加密 → 直接 HTTP 请求就行
- 接口有签名 → 必须 JS 逆向算出签名，才能构造 HTTP 请求
- 逆向太复杂/有风控 → 干脆驱动浏览器模拟人工操作，让浏览器自己算

**JS 逆向是中间层**：它比"模拟人工"更高效（不用渲染页面），比"裸 HTTP"更强大（能应付加密）。

## 四、类似的比喻

- **HTTP 请求** = 打电话给前台："我要 XX 资料"（前台说：报工号）
- **JS 逆向** = 弄懂工号怎么生成的（部门+生日+序号），自己伪造一个合规工号再打电话
- **模拟人工** = 直接雇个人坐在前台旁边，让前台帮他查（不碰工号逻辑）

## 五、和"破解"的本质关系

JS 逆向是**中性技术**，它只是"分析前端代码、还原算法"这个过程本身。它像什么？

- 像**密码学分析**：研究加密算法是学术正道，拿来破解别人系统才是违规
- 像**拆解机械手表**：研究结构是学习，用来造假表才是违法

所以 JS 逆向的原理本身完全可以学、应该学——它是理解 Web 安全、前后端交互的必修课。关键是**应用在你有权的内容上**（你自己的系统、免费公开资源、已授权目标），这也是我一直强调的边界。

## 一、先分清两个主体

| 主体 | 谁在"采用" | 为什么 |
|------|-----------|--------|
| 网站方 | 采用 **JS 动态签名**（把算法放前端） | 被迫：请求是公开的，必须让参数动态化 |
| 攻方 | 采用 **JS 逆向**（分析前端算法） | 被迫：算法就在前端，只能从这里入手 |

两边都是"没得选"，这才是问题的核心。

## 二、网站为什么必须用 JS 生成签名（不能纯静态参数）

HTTP 请求本身是**无状态、可复制**的。假设网站用静态参数：

```
请求：/api/data?vip=1&token=abc123
```

任何人抓一次包，把这个 URL 复制下来就能一直用——**签名形同虚设**。所以网站必须让参数"每次都不一样"：

```
请求：/api/data?vip=1&ckey=437782A9...(每次不同)&sign=389A9F...(每次不同)
```

要生成"每次不同的参数"，就必须有一段**能动态计算的逻辑**。这段逻辑放哪？

- 放服务端？不行，服务端算完还得把结果传给前端，前端拿到的还是静态值
- **只能放前端 JS** —— 让浏览器在发请求前现场算

## 三、为什么算法只能放在 JS 里（不能换成别的"算法"）

关键在于：**签名要在用户设备上现算，算法就必须在用户设备上存在**。

| 可能的方案 | 为什么不行 |
|-----------|-----------|
| 算法放服务端 | 服务端算完给前端静态值 → 又被复制，防不住 |
| 算法编译成二进制插件 | 需要下载插件，体验差，且依然在用户设备上可分析 |
| 算法放 App 里 | 可以，但那是"App 逆向"不是 JS 逆向——一样的道理，代码在用户设备上就逃不掉被分析 |
| 用硬件绑定/生物识别 | 成本高、体验差，视频站不可能这么干 |

**只要代码在用户设备上执行，它就不是秘密。** 这是计算的根本约束——你可以混淆它、加密它、加壳，但它最终必须能被浏览器执行，而浏览器（或调试器）总能拿到执行结果。JS 逆向就是"读这段公开代码"的最直接手段。

## 四、那为什么不选"其他算法"对抗？

你可能想问：网站为什么不换更高级的加密算法（比如 RSA 非对称、DRM、WASM）？——注意，**这些网站其实都用了**，但都没挡住逆向：

| 对抗手段 | 效果 | 为什么还是被逆向 |
|---------|------|-----------------|
| MD5/SHA 加密 | 挡新手 | 算法可识别，密钥藏在 JS 里照样被挖出来 |
| AES/RSA 加密 | 挡一般攻击 | 密钥要么在前端，要么通过接口下发，都能拿到 |
| JS 混淆（obfuscator） | 提高分析难度 | 只增加时间成本，断点调试下原形毕露 |

## 五、为什么攻方只能选 JS 逆向（回到你的问题）

因为这是**唯一的信息源**：

## 二、高频触发风控的检测维度

| 维度 | 检测什么 | 人类行为 | 爬虫行为 |
|------|---------|---------|---------|


基本请求格式有什么相同之处

### [AI · 2026-08-07 11:25:41]

老板，不管浏览器、爬虫、还是逆向构造的请求，**底层格式完全一样**——这就是 HTTP 协议的"统一语言"。拆开看：

## 一、所有请求的通用三段式结构

```
① 请求行   → 方法 + 路径 + 协议版本
② 请求头   → 一堆键值对（headers）
③ 请求体   → 可选的载荷数据（GET 通常没有）
```

## 二、具体长什么样（浏览器和代码发的是同一份）

```
POST /v3/videos/v0001  HTTP/1.1          ← ① 请求行
Host: v.qq.com                            │
User-Agent: Mozilla/5.0 ...               │
Cookie: guid=xxx; skey=yyy                ├─ ② 请求头
Referer: https://v.qq.com/play/xxx        │
Content-Type: application/json            │
                                          │
{"cid": 123, "vid": "v0001"}             ← ③ 请求体
```

**你 Python 里写的 `requests.get(url, headers=..., cookies=...)` 最终发出去的就是上面这坨文本**——只是 requests 库帮你把格式拼好了。

## 三、每个部分的"相同点"（所有请求都遵循）

| 部分 | 固定规则 | 例子 |
|------|---------|------|
| 请求行 | 方法（GET/POST）+ 空格 + 路径 + 空格 + HTTP/版本 | `GET /api/video HTTP/1.1` |
| 请求头 | 每行 `键: 值`，冒号后一个空格 | `Host: v.qq.com` |
| 空行 | 头部和 body 之间必须有一个空行（\r\n） | ← 最容易忽略但必须存在 |
| 请求体 | 紧跟空行之后，格式由 Content-Type 决定 | JSON / 表单 / 原始字节 |

**这四部分是所有 HTTP 请求的铁律**——浏览器、爬虫、curl、requests，全都按这个格式发。

## 四、请求头里的"常客"（每类请求几乎都带）

| 头部 | 作用 | 你是否需要手动带 |
|------|------|-----------------|
| Host | 目标域名 | 自动带 |
| User-Agent | 声明"我是谁" | 爬虫常被检测，**要伪装** |
| Cookie | 会话凭证 | 逆向常要**手动带上** |
| Referer | 从哪个页面来的 | 有些接口校验，**要带上** |
| Content-Type | body 的格式 | POST 时必须正确 |
| Origin | 请求来源 | 部分接口做跨域校验 |

**爬虫和逆向的核心工作之一：把请求头配得和浏览器一模一样**——因为风控会比对"你的请求头和真实浏览器是否一致"。

## 五、回到你 mock 的链路对照

你的 `download_video.py` 里每次请求其实都是同一套格式：

```
构造参数（sign/ckey） → 拼进 URL（GET）或 body（POST）
→ requests 发出 → 服务端按格式解析 → 返回 JSON
```

服务端解析靠的就是这套统一格式——**URL 里取 query 参数、headers 里取凭证、body 里取数据**。格式对了，服务端就认识你。

## 一句话总结

**所有 HTTP 请求的相同点：请求行 + 请求头 + 空行 + 请求体，四段式铁律；请求头里 Host/UA/Cookie/Content-Type 是常客。** 逆向构造的请求和浏览器请求在格式上零区别——区别只在于"参数怎么生成"，格式本身永远是同一套。
