## 方案二：自建 NAS 共享记忆后端（数据完全自控）

如果你希望记忆数据不出网、或者官方同步不够灵活，可以自建。Hermes 的记忆分三层：

| 层级 | 存储位置 | 可共享 |
|------|----------|--------|
| 会话历史 | 各设备本地 `state.db`（SQLite） | 否 |
| 内置记忆 | 各设备本地 `MEMORY.md / USER.md` | 否 |
| 语义记忆 | Hindsight 后端 | **是，可跨设备** |

核心思路：在 NAS 上用 Docker 部署 Hindsight + PostgreSQL，各设备配置文件改为指向同一个后端和同一个 bank_id。

**操作要点：**

1. NAS 上 `docker compose` 起 Hindsight API Server（端口 8888）+ PostgreSQL
2. 各电脑的配置文件 `%LOCALAPPDATA%\hermes\hindsight\config.json` 改为：
   ```json
   {
     "mode": "local_external",
     "api_url": "http://你的NAS地址:8888",
     "bank_id": "hermes",
     "recall_budget": "mid",
     "timeout": 120
   }
   ```
3. **关键**：所有设备的 `bank_id` 必须完全一致（如都写 `"hermes"`），否则各自为独立记忆库

网络方案选一种：
- 局域网：直接填 NAS 内网 IP
- 异地：用 Tailscale / ZeroTier / 节点小宝 P2P 组网，填虚拟 IP
- 公网：Nginx 反代 + HTTPS

### [AI · 2026-08-08 15:50:26]

对比"整目录同步"和"只共享记忆层"，负担差别很大：

| 维度 | OneDrive 同步整个 home 目录 | 只共享记忆层（Hindsight） |
|------|---------------------------|---------------------------|
| 磁盘占用 | 全量同步（会话库 state.db 动辄几百 MB，加上技能库、日志、缓存轻松上 GB） | 只同步提取后的记忆文本+向量，通常几十 MB 以内 |
| 同步流量 | 文件一变更就上传，实时同步频繁触发，双向都耗带宽 | 只有对话结束、记忆被提炼后才写入一次，流量极小 |
| 并发冲突 | 两台同时读写同一 SQLite → 锁冲突、卡死 | 各电脑本地库独立，共享端是 PostgreSQL 服务，天然支持多客户端并发 |
| 本地资源 | 同步工具持续监控文件变化，CPU/内存/IO 都被占用 | 本地零负担，只有 recall 时才发起一次 API 请求 |
| 冲突副本 | 频繁产生 "xxx-Conflict" 副本，还得手动清理 | 无冲突概念，Hindsight 有自动去重合并（consolidation） |

**一句话量化**：负担从「每台电脑都要实时同步上 GB 的文件 + 频繁冲突处理」降到「一台 NAS 上跑两个容器（约 1.1GB 内存），各电脑几乎零额外开销」。

**代价是什么**：原始会话记录不同步。也就是说，你在 A 电脑的完整对话原文，B 电脑上查不到——B 只能通过 recall 拿到 A 侧被提炼出来的记忆要点。如果你需要的是「逐字同步所有聊天记录」，记忆共享方案满足不了；如果你需要的是「B 电脑知道 A 电脑聊过什么、记得你的偏好和工作流」，它绰绰有余。
