## 方案一：版本备份（最轻量）

把 Obsidian 仓库（Vault）初始化为 Git 仓库，定期手动提交。

```bash
cd "你的Vault目录"
git init
git add .
git commit -m "备份"
git remote add origin git@github.com:你的用户名/仓库名.git
git push -u origin main
```

适合：偶尔备份，不怕丢笔记。

## 方案二：Obsidian Git 插件自动同步（推荐）

安装社区插件 **Obsidian Git**，设置后自动定时 commit + push。

**配置步骤：**
1. Obsidian 设置 → 第三方插件 → 关闭安全模式 → 浏览社区插件 → 搜索 "Obsidian Git" → 安装
2. 插件设置中配置：
   - 自动提交间隔（如每 30 分钟）
   - 开启 "Pull updates on startup"（启动时拉取远程更新）
   - 开启 "Push on backup"（提交后自动推送）
3. Vault 目录需先 `git init` 并关联远程仓库

适合：多设备同步（PC ↔ 笔记本），无需 Obsidian Sync 付费。

## 方案三：GitHub Pages 发布知识站点

用 Obsidian 写笔记，通过 GitHub Actions 自动构建发布为静态网站。

**常用轮子：**
- **[Quartz](https://quartz.jzhao.xyz/)**：最流行的 Obsidian → 网站工具，支持双链图谱、全文搜索
- **[Digital Garden](https://dg-docs.ole.dev/)**：Obsidian 插件，一键发布到 GitHub Pages

**大致流程：**
```
Obsidian 写作 → git push → GitHub Actions 触发 → 构建静态站 → GitHub Pages 上线
```

适合：公开知识库、个人博客、团队文档站。

## 1. Obsidian 同步的是什么

同步的是**整个 Vault 文件夹里的所有文件**——主体是 `.md`（Markdown），也包括附件（图片、PDF、音频等）。Obsidian 不会对文件做格式转换，它就是在本地的纯文件上工作，同步只是把这些文件搬到另一台设备。

## 2. Python 或其他类型文件怎么办

Obsidian **不转换文件格式**，但它能处理非 Markdown 文件：

| 做法 | 效果 |
|------|------|
| 直接拖入 `.py` 文件 | 作为附件存储，可在笔记中 `[[链接]]` 引用，但不能在 Obsidian 里编辑 |
| 内嵌代码块 | 把代码粘贴到 `.md` 文件的 ` ```python ` 代码块里 |
| 社区插件 `Code Files` | 允许 Obsidian 直接打开和编辑 `.py`、`.js` 等代码文件 |

**核心原则**：Obsidian 的笔记主体必须是 Markdown，其他格式只能作为附件引用，不能被 Obsidian 当作可编辑笔记。它不是 IDE，不适合大量管理代码文件。

## 3. 使用中的常见困难

- **入门曲线**：双链 `[[ ]]` 的思维方式需要适应，从文件夹层级转向网状关联有学习成本
- **文件堆积焦虑**：不像 Notion 有数据库视图，文件多了容易散乱，依赖个人整理纪律
- **插件膨胀**：插件多了会拖慢启动速度，且插件间可能冲突
- **同步踩坑**：非官方 Sync 方案偶尔出现文件冲突、`.obsidian` 配置不同步的问题
- **移动端体验降级**：部分桌面端插件在手机端不可用
- **图片管理**：本地图片会让仓库体积快速增长，图床方案又增加复杂度

最后一点——Obsidian 适合**以文字为主的深度思考**，如果你日常大量产出的是 Python 代码而非文字笔记，GitHub 本身可能就是更自然的管理工具，不必硬套 Obsidian。

Cloudflare 是一家网络基础设施公司，但对你真正有价值的是它的**免费开发者生态**。

## 核心免费服务

| 服务 | 用途 | 你的场景匹配 |
|------|------|-------------|
| **Workers** | 边缘计算，跑 JS/Python 脚本，无需服务器 | 影刀指令里需要外部 API 对接时，Workers 可以当中间层 |
| **Pages** | 静态网站托管，push Git 自动部署 | 如果有文档站或 RPA 指令说明页，免费部署 |
| **D1** | 边缘 SQLite 数据库，配合 Workers 用 | 脚本需要存储数据但不想搭服务器 |
| **R2** | 对象存储，免流量费 | 存储脚本产物、日志、截图 |
| **Tunnel** | 内网穿透，把本地服务暴露到公网 | 远程调试本地脚本服务 |
| **Queues** | 消息队列 | 多脚本间的异步任务编排 |

## 对你有没有用

- **需要对外暴露 API 但不想买服务器** → Workers 免费额度每天 10 万次，够用
- **脚本需要落地存储** → D1 + R2 比自建数据库省心
- **不方便搭服务器但有公网需求** → Tunnel 一条命令把本地端口穿透出去

但前提是你**确实有"脚本需要联网服务"的场景**。如果你目前所有脚本都是纯本地运行、不需要外部 API、不需要存储，那 Cloudflare 暂时用不上。
