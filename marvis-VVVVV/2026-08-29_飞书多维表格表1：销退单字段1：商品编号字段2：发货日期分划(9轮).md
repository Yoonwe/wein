**为什么需要**：`2026/06/11` 是文本，文本之间用 `<`、`MAX` 比较是按字符逐个比的，斜杠和横杠的 ASCII 不同会导致 `2026/06/11` 和 `2026-08-23` 比较结果错乱。转成 8 位数字后，`20260611` 是数值，数值比较天然等于时间先后，且 `MAX` 能直接取最大。

## 字段 2（表1）「目标日期」

```
MAX([SKU-69-采购价].FILTER(AND(
  CurrentValue.[商品ID-JD]=[商品编号],
  CurrentValue.[日期数字]<=VALUE(SUBSTITUTE([发货日期分划], "-", ""))
)).[日期数字])
```

**原理**：从右往左拆：
- `[SKU-69-采购价].FILTER(条件)`：在表2 里筛行，条件是 `AND(条件A, 条件B)` 同时满足。
  - 条件A `CurrentValue.[商品ID-JD]=[商品编号]`：`CurrentValue` 在 FILTER 里代表"表2 正在被判断的那一行"，所以是"表2 的商品ID-JD 等于表1 当前行的商品编号"——这就是你说的必要条件，把同商品的多条记录圈出来。
  - 条件B `CurrentValue.[日期数字]<=VALUE(SUBSTITUTE([发货日期分划], "-", ""))`：表2 该行的日期数字，小于等于表1 当前行发货日期转换成的数字。即"只保留发货当天或之前已生效的日期"。
- `. [日期数字]`：把筛选出来的那些行的「日期数字」字段抽出来，组成一个数组，比如 `[20260611, 20260620, 20260715]`。
- `MAX(...)`：取这个数组的最大值，就是"同商品、且不晚于发货日期的那批日期里，最晚的一个"——即目标日期。

**为什么这样写**：这一步是两次筛选之间的桥梁。它把"取最大日期"这个需要嵌套逻辑的动作，先算成一个普通字段值存下来，后续字段直接引用这个值，从而避开 FILTER 套 FILTER。

## 字段 3（表1）「目标条码」

```
[SKU-69-采购价].FILTER(AND(
  CurrentValue.[商品ID-JD]=[商品编号],
  CurrentValue.[日期数字]=[目标日期]
)).[条码].FIRST()
```

**原理**：再次筛表2，条件变成"同商品 + 日期数字**精确等于**目标日期"，这样筛出来的就是目标日期当天那一行（或几行）的记录；`. [条码]` 取出这些行的条码组成数组；`.FIRST()` 取数组第一个，即目标条码。

**为什么这样写**：用字段 2 算出的具体日期值做等值匹配，条件里只有字段引用，没有函数嵌套，所以安全。如果同一天恰好有多条记录，`FIRST()` 取行序第一条。

## 字段 4（表1）「最终条码」

```
IF(LEFT([目标条码],2)="69",
  [目标条码],
  [SKU-69-采购价].FILTER(AND(
    CurrentValue.[商品ID-JD]=[商品编号],
    CurrentValue.[日期数字]=[目标日期]
  )).[条码转映射].FIRST()
)
```

**原理**：`LEFT(文本, 2)` 取条码前两位，判断是否为 `"69"`（即原公式里的 69 前缀规则）：
- 是 → 直接输出目标条码；
- 否 → 用与字段 3 完全相同的筛选条件，去取同一天那行的「条码转映射」输出。

**为什么这样写**：它复用了字段 2 的目标日期，整个公式里依然只有一次 FILTER 调用（在 IF 的假分支里），不触发嵌套限制。

## 整体流水线

```
表2 日期转数字 ──► 表1 筛出"同商品+不晚于发货日期"取最大日期
                       ──► 按该日期精确匹配取条码
                            ──► 69 前缀判断，输出条码或条码转映射
```

每一步都只做一件事、每个公式只出现一次 FILTER，靠「目标日期」这个中间字段把两次筛选衔接起来——这就是整套方案能绕开飞书公式嵌套限制的设计核心。
